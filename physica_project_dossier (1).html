01 / Practical use

What is PHYSICA actually used for?

The main use is to turn a video or motion dataset into a small, evidence-led investigation: measure motion, test competing explanations, predict an unseen part, and check the prediction against an independent observation.

THE WHY
The problem PHYSICA addresses

A video shows what happened. PHYSICA aims to test which model explains it—and whether that model can predict what happens next.

A normal video player lets you watch movement. A basic tracker gives you positions. A calculator evaluates an equation you already chose. PHYSICA is designed to connect those steps: it extracts measurements, compares candidate motion equations, refuses an unreliable winner, predicts a withheld part of the motion with uncertainty, and reports how that prediction compares with a later measurement.

The intended scientific output
01 measured position vs time02 selected model—or no reliable model03 predicted value + interval04 later observation + error
The main uses
⚗

Teach experimental physics

Give students a transparent investigation to follow: define the setup, measure motion, estimate a model, state uncertainty and discuss why measurement quality affects a conclusion.

ƒx

Compare possible explanations

Test candidate equations such as constant, linear and quadratic motion models against the same observations. The software should choose only when selection criteria support a choice—not because one curve looks attractive.

↗

Test a prediction on unseen data

Fit using an earlier segment, predict at later timestamps that were withheld from fitting, then compare with the actual measurement using an interval-aware verdict and honest errors.

◎

Make measurement quality visible

Expose coordinate units, calibration, uncertain points, missing frames, extrapolation and interval assumptions instead of presenting every number as equally trustworthy.

↻

Make experiments repeatable

Use recorded clips and deterministic synthetic cases to reproduce an analysis, debug a model and compare results between runs. Long-term append-only evidence storage remains a separate integration task.

⌁

Build toward broader motion studies

The first experiment is a ball moving down a ramp. Later, the same workflow could be adapted to other motion datasets—provided the sensor, calibration, candidate models and validation tests are appropriate.

Why this is more than a tracker

It tests how well a model generalizes

A curve can fit known points and still predict new points poorly. PHYSICA's intended value is to reserve observations for testing and compare predictions with those unseen measurements, rather than judging success only by how closely a curve follows the data used to fit it.

  • Compare several candidate models using a defined selection process.
  • Keep the selected equation, uncertainty and extrapolation status visible.
  • Allow “no reliable model” or “inconclusive” instead of forcing a confident answer.
Why this is more than a calculator

The equation is tested—not assumed

The user should not need to declare in advance that the ball follows one particular equation. PHYSICA evaluates the candidate families available to it and can report when the evidence is insufficient. Symbolic discovery of entirely new relationships is a later roadmap phase, not a completed capability.

  • Predictions remain distinct from observations.
  • Intervals express uncertainty, not guarantees.
  • A successful software test is not a substitute for a real experiment.
Available in reported code

The scientific core

Candidate fitting, model-selection safeguards, point prediction, bootstrap predictive intervals, a prediction CLI, and the Phase 9 numerical comparison API have been reported implemented and tested. The leakage guard is the current next step.

Still to integrate

The complete real-world experience

The full recorded-ramp end-to-end acceptance, robust observed-evidence persistence, camera-to-analysis workflow, and polished interactive dashboard have not been reported as complete. The visual dashboard is a target—not a live application in this dossier.

One-sentence explanation for a science-fair judge

“PHYSICA turns a video of a moving object into a scientific test: it measures the motion, compares possible equations, predicts a part it has not used for fitting, and checks that prediction against what was actually observed—while showing uncertainty and admitting when the evidence is not enough.”

What it does not claim

PHYSICA does not automatically discover every law of nature, replace careful experimental design, or guarantee correct predictions. It evaluates the candidate models and data available to it. The physical-camera pipeline and polished UI still need to be integrated and demonstrated end to end.

02 / What we are building

What exactly are we building?

The project combines computer vision and scientific model comparison into an auditable workflow. The previous section explains why that workflow is useful; this section defines exactly what PHYSICA is being built to do.

THE MISSION
◉

Observe the real world

Acquire frames or a recorded clip, find the moving object, track its centre over time, retain quality flags and preserve image-space versus calibrated-world coordinates.

ƒx

Discover a supported model

Fit multiple candidate equations to measured data, compare how well they explain it, inspect residuals and refuse to select a model when the evidence is unreliable.

↗

Make a falsifiable prediction

Predict a value at an unobserved time, publish uncertainty and model provenance, then compare the prediction with a later observation instead of calling the guess a fact.

Scientific positioning

PHYSICA does not prove or discover universal laws of nature from one run. It evaluates which candidate models are best supported by its measurements, assumptions and validation results.

04 / Scientific engine

How PHYSICA reasons about motion

The core uses candidate equations and numerical fitting. Model choice is based on evidence from the data, not a hard-coded rule that says every ramp experiment must follow a particular equation.

EQUATIONS + EVIDENCE
Baseline / null model

Constant

Checks whether a changing-motion model provides meaningful improvement over a no-motion baseline.

y(t) = cOne fitted parameter
First-order trend

Linear

Useful for approximately constant velocity over the measured interval.

y(t) = c₀ + c₁tIntercept + slope
Acceleration candidate

Quadratic

Represents constant acceleration in one coordinate when the assumptions are appropriate.

y(t) = c₀ + c₁t + c₂t²For this parameterization, acceleration is 2c₂
Flexible polynomial

Cubic

Can capture more complex curvature, but additional parameters can overfit a short or noisy run.

y(t) = c₀ + c₁t + c₂t² + c₃t³Complexity must be penalized
Nonlinear candidate

Exponential

Available as a competing family; it must not be chosen merely because a nonlinear optimizer succeeds.

y(t) = A e⁻ᴮᵗ + CParameters and domain matter
Periodic candidate

Sinusoidal

Can represent oscillatory observations. Frequency and timestamp scale need careful treatment.

y(t) = offset + A sin(2πft + φ)Frequency, amplitude and phase
Coupled channels

Projectile-style model

A coupled model predicts horizontal and vertical channels with the same parameter vector. The fitted vertical acceleration is not replaced with a textbook constant.

x(t) = x₀ + vₓt
y(t) = y₀ + vᵧt + ½aᵧt²Shared model; distinct x/y outputs
Reliability

Residual checks & uncertainty

Model quality is not just a curve that looks smooth. Residual structure and the uncertainty assumptions affect whether a prediction should be trusted.

error = observed − predictedResidual diagnostics and resampling
Prediction

Bootstrap predictive interval

Step 2 of Phase 8 resamples rows, refits the chosen family and adds a documented observation-noise term.

[lower percentile, upper percentile]Not a guarantee; assumptions and coverage must be reported
How model selection should behave

Metrics work together

RMSE and MAE summarise residual magnitude; R² describes a particular variance-based fit comparison; AIC/BIC penalize complexity under their assumptions; cross-validation and residual checks provide complementary evidence. There is no single score that makes every scientific decision safe.

“I don't know” is a valid answer

If data are insufficient, candidates fail, residuals are unreliable or no candidate clears selection criteria, PHYSICA should return a refusal/no-reliable-model result instead of manufacturing a confident prediction.

Reliability gate No forced winner
Predictive interval ≠ parameter-confidence band

A parameter band describes uncertainty in the fitted model's estimated response. A predictive interval must also represent noise expected for a new observation. Current bootstrap intervals rely on explicit assumptions, including row-resampling independence and a noise model; real video data can have correlated measurement errors.

Coding principles
01

Deterministic core

Same scientific inputs and seed should give the same result. No random ID minting inside pure calculations.

02

Typed result objects

Fits, predictions and validation results carry structured fields and explicit refusal paths rather than opaque text.

03

Units are data

Pixels and calibrated metres stay distinct. A pixel result must never silently become an SI measurement.

04

Tests before claims

Acceptance claims should link to reproducible tests or real experimental output—not screenshots alone.

Phase 9 validation outcomes
MATCH

Inside interval

The observed value lies within the predictive interval, including its endpoints. This describes interval containment, not proof of a correct law.

MISS

Outside interval

The observation falls outside a valid interval. Report error and extrapolation status; one miss alone does not explain why the model failed.

INCONCLUSIVE

No usable interval

There is no valid interval to evaluate, or the comparison inputs are genuinely absent in a supported path. Invalid input must never become a fake match.

09 / Verification

How we know the code is behaving

The testing strategy uses exact cases, noisy synthetic data, deterministic seeds, refusal paths, serialization checks and regression tests. A passing test suite supports software correctness; it does not replace a real physical experiment.

REPRODUCIBLE SCIENCE
Unit / API tests

Small invariants

Model evaluation, parameter shapes, units, timestamp alignment, finite outputs, typed errors, schema checks and public imports.

Synthetic experiments

Known ground truth

Generate exact and noisy trajectories, fit only training rows, request held-out predictions and calculate coverage/errors against known values.

Regression suite

Keep old phases stable

After every new phase, rerun the entire suite so new validation behavior does not alter earlier fitting, selection or prediction behavior.

What a green suite proves—and what it doesn't

It proves that the tested code paths met asserted contracts under those fixtures. It does not prove the webcam tracks every real ball reliably, the calibration is accurate in your lighting, or that a selected candidate is a universal physical law.

10 / Scientific honesty

Known limitations and guardrails

These are important because the product is a science-fair invention. Honest limitations make the project more credible, not less.

TRUST BY DESIGN
TopicWhat we knowWhat we must do
Prediction uncertaintyBootstrap predictive intervals are implemented with a residual/noise assumption.Report interval level, method, failures, extrapolation and assumptions. Never treat 95% as a guarantee.
AutocorrelationRow bootstrap assumes observations behave sufficiently independently; video frames can be strongly correlated.Disclose the limitation and consider block resampling/temporal uncertainty analysis when justified.
ExtrapolationPredictions outside training timestamps can be fragile, especially for exponential/periodic models.Keep explicit per-query flags and assess held-out tails separately.

Percentage errorIt is undefined at exact zero observed value and unstable near zero.Return unavailable with an explanation where denominator is zero; do not silently invent a near-zero threshold.

12 / Science-fair delivery

The demonstration story

A strong demo is an experiment with a question, a measurement, a model, a prediction and a test—not merely a screen that looks technical.

M1 · ONE HONEST NUMBER
Demo sequence

One run, shown step by step

  1. Mount the camera and show the ramp, known length and ball.
  2. Record or replay a short clip and display detected centre/trajectory.
  3. Show calibration, data quality and how many usable observations remain.
  4. Show candidate models and explain why one was selected—or why no reliable model was selected.
  5. Fit on earlier measurements only, then predict a later, unseen time or position.
  6. Reveal the held-out observation and report interval containment, absolute error and percentage error when defined.
  7. State the limitation: one run tests a model under these conditions; it does not establish a universal law.
Plan for failure

Demo-day fallback

  • Have a known-good recorded ramp clip in addition to a live-camera attempt.
  • Clearly label replay versus live capture.
  • Keep an offline synthetic run for testing the software, never pass it off as measured data.
  • If quality gates refuse the model, explain why instead of forcing a winner.
  • Keep a printed one-page architecture / result summary for visitors and judges.
  • Rehearse a cold start and confirm the app still runs without internet.
Suggested one-sentence explanation

“PHYSICA tracks a ball, fits and compares several possible motion equations, predicts an unseen part of the movement with uncertainty, and checks that prediction against a later measurement—while keeping the prediction separate from the observation.”

14 / Reference

A–Z glossary

The vocabulary a developer, partner or science-fair judge should be able to use when explaining PHYSICA.

QUICK REFERENCE
Calibration
Relating image coordinates to a physical reference, such as metres per pixel.
Candidate model
A possible equation fitted to the observed data; it is a proposal to test, not a truth.
Coordinate source
Where the position came from, such as pixel/image space or calibrated world space.
Cross-validation
Repeatedly evaluating how well a fit generalizes to rows not used to fit that fold.
DatasetRecord
A typed record containing an observation/time and available coordinate, state and uncertainty fields.
Determinism
Reproducible results from the same inputs and controlled random seed.
Evidence ID
An identifier for an evidence record. A model/dataset/trajectory ID is not automatically an evidence ID.
Extrapolation
Prediction outside the timestamps or input domain represented by the data used to fit the model.
FitResult
Structured result of fitting a model, including parameters, status, used rows/times and residual information.
Ground truth
A known synthetic value or independent trusted reference used to test error; real data rarely has perfect ground truth.
Held-out observation
A measurement intentionally excluded from fit and selection, then used afterward to assess a prediction.
Interval coverage
The fraction of target values that fall inside the reported intervals over a defined repeated test.
MAE / RMSE
Mean absolute error and root mean squared error, common summaries of residual magnitude.
Model selection
The explicit procedure for choosing among eligible candidates while accounting for fit, complexity and reliability.
OBSERVED
A measurement from the world or a recorded input; it must not be replaced by a model's estimate.
PREDICTED
A model-produced value for a future or unobserved point, ideally accompanied by uncertainty and provenance.
Residual
Observed value minus fitted model value for a data point used in fitting.
Selection verdict
Whether a model is scientifically eligible/selected; a lowest score alone does not guarantee selection.
Uncertainty
Quantified limitations in an estimate or a new measurement; an interval is not a promise.
Validation
Comparing a prior prediction to a separate observation using defined alignment and outcome rules.
WebSocket
A persistent browser/server communication channel suitable for streaming status and measurement updates.
Zero-denominator error
